Serverless na prática

Serverless tem servidor, sim. Só não é você que cuida dele. Você entrega o código ou a imagem, a nuvem roda, escala e cobra pelo uso. Nesta lição, a Mel da Zumi aposenta a VM e descobre a paz.

1. Pagar só quando alguém chama

Lembra da VM da loja que alguém precisava atualizar e reiniciar? Com serverless, essa pessoa some da história. A nuvem liga o seu código quando chega uma requisição ou um evento e desliga quando acaba.

  • Sem chamada, quase sem custo. Uma API que recebe cem acessos por dia custa centavos, ou nada, na faixa gratuita.
  • Escala sozinha. Chegou uma enxurrada de pedidos? A nuvem roda várias cópias.
  • Menos coisa para quebrar. Sem sistema operacional para atualizar, sem disco para encher.

2. Funções rodam um pedaço de código por evento

Uma função acorda com um evento, faz uma coisa e termina.

  • AWS: Lambda.
  • Google Cloud: Cloud Run functions (o antigo Cloud Functions agora faz parte do Cloud Run).

Exemplos de evento:

Quando acontece...a função...
Chega uma foto nova no bucketgera a miniatura para o site
O sistema de pagamento avisa que o Pix caiumarca o pedido como pago e manda o e-mail
Bate meia-noitegera o relatório de vendas do dia
Alguém chama GET /estoqueresponde com o JSON do estoque
Uma função em Python que responde HTTP, no formato do Lambda:
def lambda_handler(event, context):
    return {"statusCode": 200, "body": '{"potes": 42}'}

3. Contêineres gerenciados rodam a sua imagem sem servidor

Se a sua aplicação já roda num contêiner Docker, você nem precisa quebrar em funções. Entrega a imagem inteira.

  • Google Cloud: Cloud Run. Recebe a imagem, devolve um endereço HTTPS e escala até zero. Tem faixa gratuita de 2 milhões de requisições por mês.
  • AWS: ECS com Fargate, ou App Runner. O Fargate cobra enquanto a tarefa está ligada e não tem faixa gratuita: apague no fim do exercício.
gcloud run deploy mel-da-zumi --source . --region southamerica-east1 --allow-unauthenticated

Esse comando pega o código da pasta atual, monta a imagem, publica e devolve o endereço. Para a Mel da Zumi, é o fim da VM embaixo do balcão.

4. Função ou contêiner? E quando não usar nenhum

Escolha pelo tipo de trabalho:

SituaçãoVá de
Reagir a um evento curto (arquivo, mensagem, horário)Função
Uma API ou site que você já tem em DockerContêiner gerenciado
Processo que roda horas sem parar, ou conexão aberta o tempo todoVM ou Kubernetes
Dezenas de serviços com controle fino de rede e deployKubernetes gerenciado (EKS, GKE), assunto da Platform Engineering

5. Cold start, logs e segredos

  • Cold start: depois de um tempo parada, a primeira chamada demora mais, porque a nuvem prepara o ambiente. Funções pequenas e com poucas dependências sofrem menos.
  • Logs: tudo o que a função imprime vai para o CloudWatch ou para o Cloud Logging. Deu erro 500? O log mostra a linha.
  • Segredos: chave de API entra por variável de ambiente ou por um gerenciador de segredos (Secrets Manager na AWS, Secret Manager no Google Cloud). No código, nunca.
  • Treinar sem conta: a AWS SAM CLI roda a sua Lambda num contêiner no seu computador com sam local invoke.

6. Missão final

1. Sua primeira função

Crie uma função que responde {"ola": "seu nome"} na AWS e no Google Cloud. Chame com curl e ache a chamada nos logs.

2. Contêiner no ar

Pegue a imagem que você criou na trilha Platform Engineering, ou um nginx simples, e publique no Cloud Run. Depois apague o serviço.

3. Escolha a ferramenta

Para cada caso, diga função, contêiner ou VM: um bot que responde no WhatsApp, um site de portfólio com backend em Node, um servidor de Minecraft e um envio de e-mail toda segunda às 8h.
