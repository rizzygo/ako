Os cinco blocos da nuvem

A AWS e o Google Cloud têm centenas de serviços cada um. A boa notícia é que quase todo projeto usa os mesmos cinco blocos. Aprenda os cinco e o resto vira variação. Para dar exemplo, vamos montar a loja online fictícia Mel da Zumi.

1. A Mel da Zumi precisa ir para a nuvem

A Zumi vende mel pela internet. O site mostra os potes, guarda os pedidos e manda as fotos dos produtos. Hoje roda num notebook embaixo do balcão, que desliga quando alguém tropeça no fio. Vamos levar para a nuvem, bloco por bloco.

Cada bloco tem o mesmo formato: o que é, para que serve, onde aparece na loja, o nome nas duas nuvens e um comando para você testar.

2. IAM decide quem pode fazer o quê

O que é. O porteiro da conta. Ele confere quem está pedindo (identidade) e se pode fazer aquilo naquele recurso (permissão).

Para que serve. Evitar que qualquer pessoa ou programa faça qualquer coisa. A regra é o least privilege: cada um com só o que precisa.

Na loja. A Zumi tem acesso de administrador. O estagiário que sobe fotos só pode gravar no bucket de fotos. O programa do site só lê e grava na tabela de pedidos. Ninguém usa a senha de ninguém.

AWSGoogle Cloud
PessoaUsuário do IAM Identity CenterConta Google ou do Workspace
ProgramaRoleService account
Conjunto de permissõesPolicy (JSON)Role (predefinida ou personalizada)
 
aws sts get-caller-identity
gcloud auth list

Os dois comandos respondem "quem sou eu agora". Rode antes de qualquer coisa que apaga.

3. A rede é a muralha, e o firewall abre as portas

O que é. Uma rede privada sua dentro da nuvem (VPC), dividida em subnets, com regras de firewall dizendo o que entra.

Para que serve. Deixar público só o que precisa ser público. O resto fica escondido.

Na loja. O site fica numa subnet pública, com as portas 80 e 443 abertas para o mundo. O banco fica numa subnet privada e só aceita conexão do site. O SSH só abre para o IP da Zumi.

  • AWS: VPC por região, security groups ligados a cada recurso.
  • Google Cloud: VPC global, subnets por região, firewall rules na rede.
0.0.0.0/0 na porta 22 é conviteRobôs varrem a internet o dia inteiro atrás de SSH e banco abertos. Libere só o seu IP, ou use o acesso pelo console da nuvem.

4. Máquina virtual é o computador alugado

O que é. Uma máquina virtual com o sistema que você escolher, quase sempre Linux.

Para que serve. Rodar qualquer coisa que precise de um servidor tradicional: um sistema antigo, um programa que precisa de configuração especial, um jogo multiplayer.

Na loja. A primeira versão do site da Zumi roda numa VM pequena com nginx. Funciona, mas alguém precisa atualizar o Linux, olhar o disco e reiniciar quando trava. Guarde essa dor para a lição de serverless.

  • AWS: EC2. Para estudar, as menores instâncias, dentro do crédito do plano gratuito.
  • Google Cloud: Compute Engine. A e2-micro tem faixa sempre gratuita em algumas regiões.
gcloud compute instances list
aws ec2 describe-instances --query "Reservations[].Instances[].[InstanceId,State.Name]"

5. Storage é o armário infinito

O que é. Um lugar para guardar arquivos de qualquer tamanho, organizados em buckets. Barato, durável e acessível por HTTP.

Para que serve. Fotos, vídeos, backups, logs e sites estáticos.

Na loja. As fotos dos potes de mel vão para um bucket. O site só aponta para elas. Os backups do banco vão para outro bucket, privado, com versionamento ligado, porque alguém sempre apaga o arquivo errado numa sexta-feira.

  • AWS: S3.
  • Google Cloud: Cloud Storage.
aws s3 mb s3://mel-da-zumi-fotos-SEU-NOME
gcloud storage buckets create gs://mel-da-zumi-fotos-SEU-NOME --location=southamerica-east1

O nome do bucket é único no mundo inteiro. Por isso o SEU-NOME no fim.

6. Banco gerenciado é o caderno de pedidos

O que é. Um banco de dados que a nuvem instala, atualiza, faz backup e mantém no ar.

Para que serve. Guardar os dados do sistema sem você virar DBA de madrugada.

Na loja. Os pedidos têm cliente, produto e endereço, e a Zumi quer relatório de vendas por mês. Num sistema grande, isso pede um banco relacional (RDS ou Cloud SQL). Para começar barato, um NoSQL como DynamoDB ou Firestore resolve, cobra por uso e tem faixa gratuita.

AWSGoogle CloudCobra como
Relacional (SQL)RDS, AuroraCloud SQL, AlloyDBPor hora ligada
NoSQLDynamoDBFirestorePor leitura, escrita e espaço
Banco relacional esquecido é o vilão da fatura do estudanteEle cobra por hora mesmo sem ninguém usar. Se for testar RDS ou Cloud SQL, crie, teste e apague no mesmo dia.

7. Os cinco juntos

Olhe a loja inteira: a Zumi entra pelo IAM, o site roda numa máquina dentro da rede, as fotos ficam no storage e os pedidos no banco. Cada peça tem nome diferente em cada nuvem, mas o desenho é o mesmo.

O desenho da Mel da Zumi:
cliente → internet → [regra de firewall: 80/443]
        → máquina com o site (subnet pública)
              ├─ lê fotos do bucket (storage)
              └─ grava pedidos no banco (subnet privada)
tudo isso com permissões dadas pelo IAM

8. Missão final

1. Desenhe a sua loja

Escolha um negócio de alguém que você conhece (uma barbearia, uma loja de bolo, um personal). Desenhe os cinco blocos para ele, com o nome do serviço nas duas nuvens.

2. Monte e desmonte

Numa das nuvens, crie um bucket, envie uma foto, crie uma VM pequena, acesse por SSH e apague tudo. Anote quanto tempo levou.

3. Ache o erro

Um colega abriu a porta 5432 do banco para 0.0.0.0/0 "só para testar". Escreva a mensagem que você mandaria para ele, com o risco e a correção, sem dar bronca.

Para fixarExplique a Mel da Zumi para alguém usando só os cinco blocos. Se a pessoa perguntar "e se o banco ficar público?", você já sabe responder.
